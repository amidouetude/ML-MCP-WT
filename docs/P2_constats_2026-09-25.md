## 4. Défaut D10 — l'empreinte n'était pas reproductible hors de cette machine

Ceci n'est pas imputable aux trois commits ; ils l'ont rendu visible.

`core.autocrlf = true` en configuration **locale** du dépôt, et **aucun
`.gitattributes`**. Les octets d'un fichier de code dans la copie de travail
dépendent donc du checkout, et son SHA-256 avec eux :

    common/digest_manifeste_reference.py
      disque (CRLF)  e3c91f01edbb3c7a8061f7de5f0ceb75192a3585c39c9489fc347ccdf6e247ca
      index  (LF)    da3e6120082d367d1022346aadd4749c94b5eb2bee567118b1fc09a33e735984

État des 129 fichiers suivis du périmètre au moment de la mesure :

| `git ls-files --eol` | n | lecture |
|---|---|---|
| `i/lf w/lf` | 100 | écrits en LF, **jamais re-checkoutés** |
| `i/lf w/crlf` | 3 | divergents aujourd'hui |
| `i/-text w/-text` | 22 | binaires |
| `i/none w/none` | 4 | vides |

Les 100 de la première ligne basculent en CRLF au premier clone frais sous
Windows. Le digest enregistré identifiait donc **une copie de travail, pas le
contenu du dépôt** : un tiers qui reclone ne peut pas le reproduire. C'est
exactement le maillon que l'empreinte existe pour fournir.

Et `git status` ne signalait **aucun** des cinq divergents du dépôt — vérifié un
par un. La propreté au sens de git et la reproductibilité de l'empreinte se
séparaient.

### Pourquoi il fallait le régler maintenant et pas après

Les neuf fichiers de `common/` entreront dans l'index en LF et ressortiront en
CRLF sur le disque au prochain checkout. Le défaut serait passé de 3 fichiers à
12 d'un coup, et de résiduel à structurel — dans le dispositif lui-même.

### Ce qui a été fait

1. `.gitattributes` posé à la racine : `* text=auto eol=lf`, extensions de code
   explicites, binaires déclarés (dont `.mlx`, qui est un conteneur OOXML malgré
   son appartenance au périmètre de code).
   **Effet sur les fichiers suivis : aucun.** 32 fichiers signalés par
   `git status` avant, 32 après — le dépôt n'a aucun fichier en `i/crlf`,
   l'index est uniformément LF.
2. Les 5 divergents re-checkoutés. Divergents restants : **0**. La référence
   Python vaut maintenant `da3e6120…`, l'empreinte de l'index.
3. Troisième catégorie ajoutée à `common/etat_proprete_code.m` : un fichier de
   code dont les octets du disque diffèrent de ceux de l'index rend le périmètre
   sale. Le contrôle lit `git ls-files --eol`, **pas `git status`** — git s'est
   tu sur les cinq divergents, et un contrôle ne doit pas dépendre d'un cache.

Vérifié **positivement**, pas seulement vu à zéro : le fichier reconverti en
CRLF au niveau octet (sha `e3c91f01…`, exactement l'ancienne version) ressort
`!! index=lf disque=crlf : EMPREINTE NON REPRODUCTIBLE`, puis restauré à
l'identique.

Une note d'honnêteté : ma première tentative de ce test positif était fausse.
J'avais réécrit le fichier via `fileread`/`uint8`, ce qui a converti l'UTF-8 en
Latin-1 et modifié le contenu, pas seulement les fins de ligne. Le contrôle
« passait » pour la mauvaise raison. Le test refait au niveau octet reproduit
l'empreinte attendue, ce qui est la seule preuve que c'est bien la conversion de
fins de ligne qui est détectée. Je n'explique d'ailleurs pas le silence initial
de git : le cache stat de l'index est l'hypothèse la plus probable, mais je ne
l'ai pas établi, et le texte du contrôle le dit.

## 7. Sur le choix A / B / C

Le compte rendu proposait A = workflow CI exécutant les tests de digest Python
et MATLAB, B = revue statique détaillée avec corrections minimales, C = rapport
de supervision seul.

**A n'est pas réalisable tel qu'énoncé.** Un workflow CI ne peut pas exécuter le
côté MATLAB : le dépôt est privé et MATLAB y exige une licence. Un CI qui
annoncerait vérifier les deux conventions en n'exécutant que Python serait un
contrôle vert qu'il faudrait croire — précisément ce que ce dispositif refuse.
La partie Python, elle, tourne en CI sans rien demander : `test_convention()`
passe déjà ici, sur les deux exemplaires.

Ce que je recommande : **B, plus la moitié réalisable de A**. Un job CI qui
exécute `python common/digest_manifeste_reference.py` et rien de plus, annoncé
comme tel ; le côté MATLAB reste vérifié à la main et la fiche dit qui l'a
vérifié et quand. C'est moins séduisant qu'un badge vert et c'est vrai.

### Deux points à lire dans le reclassement

**ETABLI ne couvre que le script d'entrée.** Les cinq séries du 13/08 sont
ETABLIES sur 57d98a4 — mais la physique NREL de `common/`
(`Tg_rated = 43093.55`) n'entre dans git qu'en `db1f75e`, le 15/08 21:29
(`git log -S`), **après** ces runs. L'état des dépendances au moment du run
n'est donc pas établi. C'est écrit dans chaque ligne concernée.

**La date prévue n'est pas la date réelle.** La régularisation était prévue le
23/09 ; elle est faite le 25/09. Le registre et les messages de commit portent
le 25/09 : inscrire le 23/09 aurait été écrire une date fausse dans le
document même qui sert à dater.

### Un défaut dans la procédure, corrigé

L'étape 7 prévoyait : commiter la fiche, relever `git rev-parse HEAD`,
l'inscrire dans `code_version`, re-commiter. **Impossible** : un commit ne
peut pas contenir son propre identifiant. La fiche re-commitée aurait porté le
hash du commit précédent, `valider_campagne.py` exige que `meta.code_sha1`
commence par `code_version`, et une campagne correcte aurait été rejetée.

Règle retenue, la même que pour les cinq champs d'identité : `stamp_campaign`
relève HEAD au lancement dans `meta.code_sha1` — ce HEAD est le commit de la
fiche, qui contient aussi tout le code, donc un seul identifiant ancre les
deux — et `code_version` est recopié **après** la campagne, dans un commit qui
ne touche que la fiche.
